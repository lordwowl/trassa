# CLAUDE.md — «Трасса» (рабочее название, codename `trassa`)

Этот файл читается в начале каждой сессии. Здесь правила проекта.
- Дизайн игры: `docs/GDD.md`
- Текущий статус и очередь задач: `PROGRESS.md`
- Настройка репозитория и CI: `docs/GITHUB_SETUP.md`

## О проекте

Мобильная игра для Android: вождение от первого лица (вид из салона) по псевдо-3D дорогам между городами условной страны. Приборная панель, зеркала, дворники, трафик, топливо, повреждения, усталость, попутчики, заправки, СТО, посты ДПС, погода, смена дня и ночи. Источник вдохновения: J2ME-игра Road Chase.

**Автор разрабатывает только с телефона через облачный Claude Code.** Из этого следуют главные требования:
1. Любой результат должен проверяться в браузере телефона по ссылке GitHub Pages сразу после мержа в `main`.
2. Все настраиваемые числа (физика, баланс, частоты событий) лежат в JSON и правятся из debug-панели в игре, без правок кода.
3. Автор не рисует. Пока нет ассетов, вся графика процедурная (рисуется кодом), и каждый спрайт можно заменить файлом без правок логики.
4. Автор не может запускать команды локально. Всё, что нужно проверить, ты проверяешь сам (`npm run check`) и пишешь в PR, что смотреть на телефоне.

## Стек

- TypeScript (`strict: true`), Vite, Phaser 3 (последняя стабильная 3.x)
- Vitest: тесты логики `core/`
- Capacitor (Android): упаковка в APK
- GitHub Actions: CI для PR, деплой на GitHub Pages, сборка debug APK
- Node 22 LTS

Новые зависимости добавлять только при явной необходимости. Каждую новую зависимость записать в `PROGRESS.md` с причиной.

## Команды

```
npm run dev        # dev-сервер Vite
npm run build      # сборка в dist/
npm run typecheck  # tsc --noEmit
npm test           # vitest run
npm run check      # typecheck + test + build (обязателен перед каждым коммитом)
npx cap sync android
```

`vite.config.ts`: `base: './'` (одинаково работает на GitHub Pages и в Capacitor).

Файлы держать небольшими: ориентир до 300 строк. Если файл растёт, разделить его.

## Архитектурные правила

1. **`core/` не импортирует Phaser и DOM.** Только типы, данные и чистые функции/классы. Рендер читает состояние из `core`, но не меняет его напрямую: только через методы или команды.
2. **Фиксированный шаг симуляции** 1/60 с с аккумулятором. Рендер может работать с другой частотой кадров.
3. **GameState** — один сериализуемый объект (без классов с методами внутри, без циклических ссылок). Сохранение — JSON с полем `version` и миграциями.
4. **Data-driven.** Города, дороги, машины, события, попутчики и тюнинг хранятся в JSON. При загрузке данные проверяются ручными type-guard'ами с понятной ошибкой (без внешних библиотек валидации).
5. **Случайность только через `core/rng.ts`** (seeded). Одинаковый seed даёт одинаковый рейс, это нужно для тестов и воспроизведения багов.
6. **Единицы:** метры, секунды, литры. Км/ч только для отображения. Деньги — целые числа.
7. **Псевдо-3D:** дорога — массив сегментов фиксированной длины с `curve`, `y` (высота), числом полос, обочинами и списком придорожных объектов. Классическая проекция сегментов (подход в духе Javascript Racer Джейка Гордона), центробежный снос в поворотах, сортировка спрайтов по дальности. Дальность прорисовки — параметр `tuning.json`.
8. **Производительность:** цель 60 FPS на Android среднего уровня. В игровом цикле никаких аллокаций; пулы объектов для спрайтов и трафика. Есть опция внутреннего разрешения (масштаб рендера 0.5–1.0).
9. **Экран:** только альбомная ориентация. Базовое разрешение 1280×720, `Phaser.Scale.FIT`, учёт safe area. На вебе кнопка «Играть» запрашивает fullscreen и `screen.orientation.lock('landscape')`.

## Тексты и язык

- Язык игры — русский.
- Строки интерфейса лежат в `data/strings.ru.json`, ключи на английском.
- Повествовательный контент (тексты событий, реплики попутчиков) пишется по-русски прямо в JSON событий.
- Код, идентификаторы, имена файлов — на английском. Комментарии — на русском, кратко и по делу.
- Кнопки не меньше 48 dp, управление удобно большими пальцами в альбомной ориентации.

## Графика

- Пока ассетов нет, используются процедурные текстуры в чистом flat-стиле: силуэты машин сзади и спереди, люди с поднятой рукой, знаки, АЗС, СТО, деревья, столбы, здания. Кабину рисует код (векторно).
- Ассеты кладутся в `public/assets/...`, каждый записывается в `public/assets/CREDITS.md` (источник, лицензия). Допустимы только CC0/свободные или сгенерированные автором.
- Все текстуры запрашиваются через `render/sprites/registry.ts`. Замена заглушки на картинку — это добавление файла и одной строки в реестре.

## Debug-режим (обязателен с M0, для тюнинга с телефона)

- `?debug=1` — FPS, скорость, обороты, передача, номер сегмента, позиция по X, погода, время. Плюс панель слайдеров для `tuning.json` (значения сохраняются в localStorage) с кнопкой «Скопировать JSON»: автор вставит его в чат, и ты перенесёшь значения в `tuning.json`.
- `?scene=drive` / `map` / `city` — сразу открыть нужную сцену.
- `?seed=123` — фиксированный seed.
- `?weather=rain|fog|clear&time=22` — принудительные погода и время суток.
- `?car=<id>&money=<n>&fuel=<l>` — стартовые условия для проверки.

## Рабочий процесс одной сессии

1. Прочитай `PROGRESS.md` и нужный раздел `docs/GDD.md`.
2. Возьми следующую задачу из очереди `PROGRESS.md` или ту, что дал автор. **Одна сессия — одна законченная, проверяемая задача.**
3. Перед кодом коротко опиши план (3–7 пунктов).
4. Реализуй. Логику `core/` покрой тестами.
5. `npm run check` должен проходить без ошибок.
6. Обнови `PROGRESS.md`: что сделано, как проверить на телефоне (ссылка и URL-параметры), что дальше, известные проблемы.
7. Коммиты в стиле conventional commits: `feat(drive): ...`, `fix(cockpit): ...`, `data(events): ...`. Описание можно по-русски.
8. Создай PR в `main`. В описании PR — чек-лист «что проверить на телефоне».
9. **Мерж PR — сам, без отдельной команды автора** (разрешено автором), если одновременно:
   - все проверки CI на последнем коммите зелёные;
   - нет конфликта с `main`;
   - нет открытых замечаний ревью;
   - PR не меняет `docs/GDD.md` (изменения дизайна мержит только автор).
   Способ — squash. Если хоть одно условие не выполнено, не мержить: исправить или сообщить автору. После мержа проверить, что workflow Pages и APK на `main` зелёные, и прислать автору ссылки.

## Чего не делать

- Не ломать `main`: туда попадает только код, прошедший `npm run check`.
- Не менять `docs/GDD.md` молча. Если дизайн нужно поменять, предложи изменение отдельным пунктом в PR.
- Не трогать `.github/workflows/` и `android/` без необходимости, связанной с задачей.
- Никогда не коммитить keystore, пароли, токены.
- Не добавлять ассеты без записи в `CREDITS.md`.
- Не реализовывать монетизацию: она будет решена позже.
